One-sentence explanationDAC100 links reviewed research claims to source-labeled process inputs, calculates bounded cost scenarios in Python, and ranks what a DAC team should investigate next.

Project in one minute

The app reproduces the Case 0B cost of capture and its modeled net atmospheric-removal basis, including the study's T&S estimate. It keeps separate verification/MRV, construction and supply-chain lifecycle emissions, and verified storage permanence outside that published result. AI extracts candidate claims, but a person must review quotes and conditions before the bounded calculation workflow can use a cost claim.

The result is a NETL conceptual model, not a commercial quote, current-dollar estimate, complete lifecycle assessment, or proof that a tonne was durably removed.

1 · Motivation

R&D choices need a shared cost boundary.

DAC researchers and commercialization leads choose which technical questions deserve scarce pilot time, engineering attention, and capital. They may be deciding whether the next experiment should focus on sorbent lifetime, regeneration energy, installed equipment cost, or the carbon intensity of available energy. Each item can matter to cost per captured tonne, but its relevance depends on plant scale, operating conditions, electricity and heat prices, financing assumptions, and the lifecycle boundary.

The intended user is therefore a technical or commercialization lead who already reads studies and vendor material and needs to connect those findings to a common process model. DAC100 is not designed to replace engineering review. It is intended to make the assumptions behind an early prioritization discussion easier to see, compare, and question.

How the task is likely handled today

The initial product hypothesis is that a user moves between papers, spreadsheets, technical notes, and informal expert discussion. A result in a paper may be a measured value from a small test, a modeled full-plant assumption, or a value calculated under conditions unlike the user’s site. Manual comparison requires the analyst to find and preserve units, the basis of a reported tonne, source conditions, financing assumptions, and whether transport, storage, verification, and lifecycle emissions are included.

This description is a design hypothesis, not an interview finding. No DAC practitioner was available for a trial before the deadline, and no task time or current-workflow cost has been measured. The report therefore does not assign a dollar cost, number of hours, or frustration score to today’s work. Those measurements would require observing a real prioritization task and asking the user to compare it with a DAC100-supported task.

Why it matters

A dollar-per-tonne value without a clear denominator or boundary can direct attention toward the wrong technical lever. Capture cost is not the same as durable net-removal cost. A low process cost can be offset by transport, storage, verification, or energy-related emissions; a tax credit can improve project economics without reducing underlying production cost. DAC100 places those distinctions beside the result so a reviewer can spot missing evidence before treating an attractive scenario as a plan.

Evidence status: Intended user and decision were defined from the project brief. User prevalence, present-day task duration, and the cost of current analysis remain unmeasured.

The first useful outcome is not a claim that DAC100 makes a DAC project cheap. It is a traceable conversation: which published cost categories drive Case 0B, which research evidence could change a cost assumption, and what must be learned before a scenario can inform the next experiment?

2 · What is new here

Join evidence review to a constrained calculation.

DAC100 works in the narrow space between a research excerpt and an auditable scenario. It associates candidate claims with named model inputs and asks for an evidence quote, unit, operating condition, and source class. The user must confirm that a measured value is comparable to the baseline before the prioritization workflow may use it. Python performs the cost math and enforces model bounds. The model cannot enter free-form replacement numbers through its tool call.

3 · The agents

One model, two bounded roles, one calculation tool.

DAC100 uses GPT-6 Luna (`gpt-6-luna`) through the course Portkey gateway. The course examples in `Lecture 12/froggy_labubu_prompt_inj/backend/config.py` and `Lecture 13/yale_som_virtual/backend/config.py` use `https://api.portkey.ai/v1` and the `x-portkey-provider: openai` header. DAC100 uses the same base URL, `PORTKEY_API_KEY`, the OpenAI provider header, and the Luna model; it does not use the course key for another model.

The AI operating roles are sequential functions of the same model alias, not a multi-agent team:

  1. Evidence extractor: receives a short, untrusted excerpt and the input catalog. It returns structured candidate claims with an input ID, numeric value when explicit, unit, short evidence quote, condition, source category, confidence, and uncertainties. This step has no tools and cannot update a model input.
  2. Research prioritizer: receives only claims the user explicitly selects and marks comparable to the current baseline. Its only tool is `evaluate_supported_scenario`, a Python function constrained to claim IDs already checked by the server. It may select at most one claim per cost lever.
  3. Deterministic calculator: validates the selected claim-to-input mapping, derives the reduction fraction in code, enforces the configured bound, calculates baseline and scenario cost, and returns the result to Luna for a conditional explanation.

Each extractor action is one request. A prioritization action is at most two requests: one tool-selection response and one explanation. There is no delegation loop, web search, file access, or external action tool.

No successful model usage was returned.

DAC100’s AI operating cost is separate from the DAC process cost per tonne. The process model produces USD per gross or net tonne; Portkey usage is priced per model call. The application records API-reported input, cached-input, and output token counts when available and estimates call cost using the course’s Lecture 11 tokenomics price sheet for GPT-6 Luna.

run cost = [(input tokens − cached input tokens) × $0.10
+ cached input tokens × $0.01
+ output tokens × $0.50] ÷ 1,000,000

Rates are USD per million tokens in the course example. This price sheet is a rate source, not a usage measurement or receipt from DAC100.

If a successful run records `I` input, `C` cached input, and `O` output tokens, then one-run cost is the formula above. At `F` runs per user-month, monthly cost is `F × run cost`; 100-user and 10,000-user totals are respectively `100 × F × run cost` and `10,000 × F × run cost`. `F` must be based on an explicit product-usage assumption.

Cost controls and tradeoffs

The extractor makes one request and caps output at 1,100 tokens. The prioritizer allows at most two requests and one tool call, with 700 output tokens per request. Both impose a 40-second per-request timeout. The app caps itself at 20 AI runs per rolling day, applies an estimated $0.05 daily spend ceiling, and limits excerpts to 8,000 characters. The estimate reserves cost using the course rate card; it is a protective limit, not measured billing.

These controls reduce runaway loops and abusive input sizes, but they do not prove an accuracy/cost tradeoff. Evaluating that tradeoff requires a successful run set and a comparison of extraction quality at different excerpt lengths or output caps. No such evidence exists yet.

Evidence rule: measured input, cached-input, and output usage is missing. An estimated token profile would be invented, so it is intentionally omitted.

7 · Limits + next steps

What must happen before this can guide a real study.

Current limits

  • NETL reproduction precision. Applying the printed Exhibit 5-13 TASC and §3.6 FCR yields $349.44/net-tonne capital cost versus Exhibit 5-16's rounded $349.6. The resulting $702.21/net-t total is $0.19 below the reported $702.4.
  • No live AI result. A Portkey attempt returned a connection-level error before any usage response. Extraction quality, live agent selection, token counts, and per-run AI cost remain unknown.
  • No practitioner trial. There is no evidence of usefulness, task time, user trust, or impact.
  • Exploratory ranges are assumptions. Four annual-cost reductions are independently varied while keeping plant output, process balance, and T&S fixed. They are not validated engineering changes and need not be compatible.
  • Lifecycle and durability are incomplete. Case 0B does not quantify construction/supply-chain emissions, storage leakage/permanence, or separate verification/MRV cost. DAC100 cannot calculate a full lifecycle cost of durable removal from this source alone.
  • Cost structure is a case reproduction. It replays NETL's annual cost totals and denominators. It is not a detailed equipment simulator and does not independently recompute the process design, sensitivity cases, financing, or policy-adjusted economics.
  • Safety controls are prototype-level. The pattern filter is not a general prompt-injection detector. Local logs are not tamper-proof; API spending limits are not an authenticated service-wide quota.
  • Deliverable gaps remain. Genuine app screenshots, public GitHub URL, independent competitor audit, print pagination, and reveal.js navigation/full-screen checks remain outstanding.

A month would allow a checked NETL benchmark with reproducible outputs; additional system configurations; provenance links and document-page references; coupled scenario constraints; sensitivity and uncertainty analysis; alternative lifecycle boundaries; a richer transport/storage/MRV module; and a small trial with at least two DAC practitioners. The highest-value next feature is not a larger agent team. It is a trusted evidence catalog and an engineering-checked baseline on which the agent can operate.

Appendix · calculation and evidence register

Formula, execution, and source status.

Capture cost per gross DAC t = (annual capital charges + fixed O&M + variable O&M + fuel) ÷ annual DAC gross capture
Project cost per gross DAC t = (capture cost numerator + T&S + separately entered verification) ÷ annual DAC gross capture
NETL net flow = (gross DAC output × assumed stored share) − modeled residual NGCC emissions
NETL-boundary cost per net t = annual included project costs ÷ NETL modeled net flow
Plant-gross COC = annual included project costs ÷ combined DAC + NGCC captured product

All quantities in this reproduction use the actual reported 85% CF annual values. The application does not multiply annual flows or annual variable/fuel costs by CF a second time. For the canonical scenario, arithmetic gives $595.53 per gross DAC tonne for capture, $616.51 per gross DAC tonne including T&S, $702.21 per NETL-boundary net tonne, and $293.82 per total-product tonne. These are within $0.2/tonne of Exhibit 5-16; in particular, applying the printed TASC and FCR yields $349.44 per net tonne for capital, rather than the exhibit's independently rounded $349.6. Source line items and totals are rounded separately.
